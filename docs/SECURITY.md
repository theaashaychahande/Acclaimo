# Security notes

Acclaimo is open source, so this document assumes an attacker has read every
line of the client, knows the Supabase project URL, and holds the publishable
key. None of those are secrets. The project is safe only because of what the
database allows, not because anything is hidden.

## What the browser is allowed to know

- `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are compiled into the
  JavaScript bundle. Both are public by design.
- The organization `salt` is returned by `get_public_org_info`, because the
  student browser needs it to hash a typed name.
- Category labels and position text (for example `Winner`) are stored in
  readable form and appear in the certificate. They are not personal data.
- The secret key and the database password are never sent to the browser and
  must never be given a `VITE_` prefix.

## What is stored

- The SHA-256 hash of a participant's normalized name, salted with a random
  per-organization value.
- The SHA-256 hash of an optional identifier when two participants share a
  name.
- The SHA-256 hash of an organizer's edit key. The key itself is shown once
  and is never stored.
- Event and organization metadata: names, dates, status, expiry, contact,
  counters, category labels, and design settings.

Plain participant names, student emails, and student accounts are never
stored. Acclaimo has no student login.

Hashing is not encryption. The salt is public, so anyone who can guess a name
can confirm whether that person is in an event. Acclaimo is a distribution
tool, not an identity check, and the public pages say so.

## Access control

- Row Level Security is enabled on every table and every table privilege is
  revoked from `anon` and `authenticated`.
- The public API is a small set of `security definer` functions. Each one
  validates its arguments and scopes writes to the organization that owns the
  edit-key hash.
- There are no public `select`, `insert`, `update`, or `delete` policies on
  the data tables. Direct PostgREST table access fails.
- Template files live in a private Storage bucket. Organizers upload through the
  `upload-template` Edge Function. It checks the edit-key hash with the service
  role, confirms the event and category belong to that organization, validates
  the image bytes, and only then writes the object and the category path. The
  service key never reaches the browser.
- The same function signs a short-lived URL for a draft preview after the same
  ownership check. The normal Storage policy still only signs templates for
  live events, so a draft or paused event does not expose its design publicly.
  Upload, replace, and delete remain service-role only.
- Default function privileges in the `public` schema are revoked, so a newly
  added helper is not callable through PostgREST until it is granted on purpose.
- Supabase Auth is not used. Email signups and anonymous sign-ins are disabled
  at the project level, so the auth endpoints cannot be used to create accounts.
- The organizer session keeps only the edit-key hash, in `sessionStorage`, for
  eight hours. Closing the tab ends it.

## Abuse limits

The database enforces a device bucket and an IP bucket for the sensitive calls:

- 3 organization creations per hour per device, and 10 per hour per IP
- 5 failed edit-key logins per 15 minutes per device, and 40 per IP
- 20 lookups per 10 minutes per organization
- a 60-second pause after 8 consecutive misses
- 8 failed admin-secret attempts per 15 minutes per device, and 40 per IP

Only failed edit-key and admin attempts count, so a busy organizer or admin is
never locked out by normal use. A successful login does not consume a limit.

The IP is read from `cf-connecting-ip`, which Cloudflare sets at the edge, and
otherwise from the last `x-forwarded-for` hop appended by the proxy. The first
value in `x-forwarded-for` is client-controlled and is ignored, so sending a
fake header does not create a fresh rate-limit bucket.

A device identifier is generated by the browser and can be cleared, so the
device bucket is best-effort. The IP bucket is the backstop. Both stop casual
enumeration and accidental retry loops; they do not stop a determined attacker
with many addresses. The salted hashes and the absence of a bulk endpoint are
the real protection.

## Deliberate limitations

- A lost edit key cannot be recovered. An admin can issue a new one after
  checking the organizer's identity out of band.
- Anyone who knows a participant's name can download that participant's
  certificate. This is the intended product behavior.
- A determined user can edit the files they download. Certificates are a
  convenience, not a cryptographic proof of attendance.
- The free Supabase tier can pause the project after long inactivity. The UI
  shows a clear error instead of a blank page.

## Deployment

- Frontend: Vercel. `vercel.json` adds SPA rewrites and a restrictive
  Content-Security-Policy.
- Backend: Supabase (Postgres, RPCs, Storage). Apply the files in
  `supabase/migrations` in order.
- Deploy the `upload-template` Edge Function with JWT verification off. It
  validates the edit-key hash itself and reads the service key from the
  function environment, never from a `VITE_` variable.
- Keep Supabase Auth signups disabled; Acclaimo never creates auth users.
- Scheduled cleanup runs nightly through `pg_cron` and also trims the
  rate-limit and lookup-strike tables so they cannot grow without bound.
- Never commit `.env`, the secret key, or the database password.

## Reporting a problem

Open a private security advisory on the GitHub repository instead of a public
issue, and include the smallest reproduction you can.
